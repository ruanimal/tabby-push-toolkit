# tabby-push-toolkit：讨论记录与初步方案

整理日期：2026-10-25

本文整理当前对话中已确认的方向、已有验证和后续建议，不代表插件已经实现。建议部分仍需开发验证。

## 1. 名称与定位

- 插件名称、仓库名：`tabby-push-toolkit`。
- 建议显示名称：Push Toolkit。
- 建议中文简介：通过 SSH 将常用工具和文件推送到精简远程环境，无需预装文件传输工具。
- 名称与用途不局限于 trzsz，以后可以覆盖脚本、配置文件和诊断工具。
- 尚未检查 npm 包名或仓库名称是否被占用。

## 2. 用户已明确的需求

1. 使用 Tabby 作为终端，开发 Tabby 插件。
2. 允许用户在设置中保存常用的、需要上传的本地文件。
3. 目标环境为类似 Alpine 的精简容器。
4. 通过现有 SSH 连接操作，连接可能经过跳板机。
5. 不依赖目标环境已有 `rz/sz`、`scp`、`sftp`、`base64`，也不依赖包管理器安装。
6. 用纯 Shell Base64 解码脚本作为初始传输手段，把适配目标平台的 trzsz 程序传入服务器，后续使用 trzsz 上传文件。
7. 通过右键菜单作为上传的入口，二级菜单选择用户已保存的文件。

这里的“无法安装”按无需系统安装和包管理器处理；仍然需要目标环境允许写入并执行用户上传的程序。若执行策略明确禁止，方案不能完成引导。

## 3. 问题背景与方案选择

常规情况下，可以使用本机 `scp -J`、SFTP 或经 SSH 标准输入传输文件。但当前讨论关注更受限的环境：只能操作已有终端会话，可能没有这些能力。

纯文本可以通过 `cat` 和带引号的 here-document 写入。二进制不能依赖直接粘贴，因为终端会解释控制字符。解决方法是在本机 Base64 编码，再由远端纯 `sh` 解码还原。

流程：

```text
Tabby 中保存常用本地文件
          ↓
通过当前 SSH 会话写入纯 sh 解码脚本
          ↓
本机编码接收端二进制，分批发送编码文本
          ↓
远端解码、检查结果、赋予执行权限
          ↓
启动远端 trzsz 接收端
          ↓
由本机支持 trzsz 的终端/插件发送后续文件
```

## 4. 已有引导脚本

脚本随本记录归档为 `scripts/base64-decode.sh`。

依赖 POSIX Shell 的参数展开、算术展开、内置 `read`、`printf`、`test` 等，不调用外部 Base64 解码器。使用 `sh script` 执行，不必先赋予脚本执行权限。

已在本机 `/bin/sh` 验证：

- 空文件、短文本和全部 256 种字节值的还原。
- 多行编码、CRLF 换行、末尾无换行。
- 对部分非法字符、错误 padding、不完整输入返回失败。

验证尚未覆盖真实 Alpine BusyBox ash 和 Tabby／跳板机链路。脚本严格要求标准 Base64 padding，不支持 URL-safe Base64。

性能限制：逐字符处理，每个输出字节使用一次命令替换，适合作为最初引导手段。几 MB 文件的实际耗时需测量。Base64 编码大小约为原文件的 4/3，另加换行。

错误限制：输入无效时可能已经写出部分文件；合法字符被错误替换也不一定能被检测。插件不能只凭“Shell 命令执行完”判断文件完整。

https://github.com/ruanimal/trzsz-rs/releases/tag/v1.3.0

讨论时未能读取该发布页及其 README，因此没有核实以下内容：

- 是否提供适合 Alpine/musl 的静态二进制。
- 接收端命令是否为 `trz`，是否为多命令共用一个程序。
- 此 Rust 实现与现有 trzsz 客户端的协议兼容程度。

文中使用 `trz` 作为示例名称，不构成该版本的实际接口保证。

应在本机解压发布包，只引导上传实际需要的接收端可执行文件，减少首传体积，避免远端还要依赖 `tar`、`gzip`。

需要按远端平台选择二进制，不能使用本机架构代替远端架构。Alpine 通常使用 musl，动态链接的 glibc 程序不一定能运行。若有适配架构的静态版本，可优先验证。

## 6. 本机终端与跳板机条件

远端传入接收程序只是其中一半。本机还需要实现或集成 trzsz 协议处理，识别远端握手并发送文件。

官方文档列出了 Tabby 的 trzsz 插件支持；本项目仍需核查其当前实现、可用 API，以及适合共存还是集成。尚未决定依赖现有插件或自行实现协议适配。

普通 SSH 会话可以承载协议数据，但网页堡垒机、字符过滤、粘贴限制、tmux 等可能影响链路。官方文档对跳板机上使用 tmux 的情况给出了 `trzsz --relay ssh` 方式，不能据此认为所有多跳场景都无需适配。

参考：

- https://trzsz.github.io/cn/py
- https://trzsz.github.io/cn/go.html
- https://trzsz.github.io/cn/js.html

## 7. 手工验证步骤

前置：已有解码脚本位于远端 `~/base64-decode.sh`；以下假设实际接收程序叫 `trz`。

本机：

```sh
base64 ./trz > trz.b64
```

远端：

```sh
sh ~/base64-decode.sh > ~/trz <<'DATA_END'
这里替换为 trz.b64 内容
DATA_END
```

只有解码成功后才继续：

```sh
chmod u+x ~/trz
~/trz --help
```

确认程序能启动且本机支持协议后，运行远端接收命令，测试后续文件上传。

注意：`>` 会覆盖文件；here-document 结束标记必须单独一行且不能与内容冲突。二进制不能通过 `sh ~/trz` 执行。远端没有 `chmod` 或等效能力时，新建文件通常不能直接执行；目标目录位于 `noexec` 文件系统时也会受阻。

## 8. 建议的首版范围（尚未确认）

### 设置

- 保存多个常用文件条目：名称、本地路径、默认远端目录。
- 对可执行工具，可配置目标文件名、是否赋予执行权限、平台和架构说明。
- 可配置用于引导的接收端本地文件，避免首版强依赖在线下载和发布资产自动解析。

### 使用流程

1. 在当前 SSH 标签页中选择一个常用文件。
2. 检查当前会话、远端路径和已存在的接收程序。
3. 接收程序可用时，直接启动协议传输。
4. 首次使用时，通过 Shell 引导传入接收程序，再传用户选择的文件。
5. 展示发送、解码和完成状态，失败时给出可操作的原因。

### 实现注意事项

- 需要独占或协调会话输入输出，不能让用户输入与文件流混合。
- 分块发送并控制速率，避免一次粘贴大量文本造成截断。
- 每阶段检查退出码；采用临时文件，验证成功后再替换目标文件。
- 在可用工具允许时比较大小和校验值；极简环境下的验证方式仍待设计。
- 对路径、文件名和 Shell 命令正确引用，防止空格、引号和特殊字符破坏命令。
- 用可靠的阶段结束标记或协议确认区分远端回显与执行结果。
- 尚未确定断点续传、取消清理、文件覆盖交互等行为。

以上是后续实现建议，不是用户已经确认的完整功能清单。
